# 品質保証基盤（QA Foundation）設計書

- 作成日: 2026-07-27
- ステータス: レビュー待ち
- 対象フェーズ: Phase 1（全3フェーズ中）

## 1. 背景と目的

OSS支援プログラム申請書（2026-07-19）に記した構想——「継続的にメンテナンスされる日本語氏名オープンデータの決定版」——を実現するための第一歩。申請書の3本柱のうち「数万件規模のエラー検出・整合性チェック」に対応する。

現状の課題:

- 約11,000エントリ（男性名 5,675・女性名 3,344・姓 2,000）は初回作成時のまま体系的な検証がされていない。
- ローマ字表記の方式が混在している（実データで確認済み: `あいいちろう→aichirou` はワープロ式、`いっしゅう→isshu` は長音省略式、`ああす→asu` は長音省略）。現行の validate.py は文字種チェックのみで、読みとローマ字の対応は検証していない。
- `ああす,asu,亜明日` のようなスクレイピング残骸と疑われるエントリが残っている可能性がある（v0.1.2 で一部除去済みだが網羅的でない）。
- 漢字と読みの対応の妥当性はルールでは書けず、LLM の判断が必要。

## 3. Phase 1 要件定義

### 機能要件

- **FR-1 決定的検証**: 全 CSV に対し、フォーマット・文字種・重複・読み⇔ローマ字対応・クロスファイル整合性を LLM なしで検証できる。CI で毎 push 実行される。
- **FR-2 LLM 検証**: 漢字⇔読みの対応妥当性、日本人名としての実在性、収録ファイル（男性名/女性名）の妥当性を Claude が判定し、疑義のみを構造化された findings として記録できる。
- **FR-3 増分検証**: 一度「問題なし」と判定されたエントリは内容が変わらない限り再検証しない（検証済みキャッシュ）。
- **FR-4 承認適用**: 人間が findings を個別に承認/却下でき、承認済みのみが一括適用される。適用後は自動で回帰検証（validate.py + pytest）が走る。
- **FR-5 レポート**: 検証実行ごとに人間が読める Markdown サマリ（疑義件数・方式混在統計・承認待ち一覧）が生成される。

### 非機能要件

- **NFR-1 コスト**: LLM 検証はローカル Claude Code（サブスクリプション枠）で実行し、API クレジットを消費しない。
- **NFR-2 安全性**: dataset CSV への自動書き込みはしない。適用は必ずユーザーの明示承認後、git ブランチ上で行う。一括自動削除は行わない。
- **NFR-3 互換性**: パッケージ本体の Python 3.8 互換を維持する（qa/ 配下と validate.py は開発ツールのためこの制約の対象外だが、既存 CI との整合を優先する）。
- **NFR-4 再利用性**: チェック関数と findings スキーマは Phase 2 の検証ゲートから import・再利用できる形に分離する。

### スコープ外（YAGNI）

- 新規データの取得・追加（Phase 2）
- スキーマ拡張・新属性（Phase 3）
- LLM 検証の CI 自動化（OSS 支援採択後に再検討）
- SQLite・レポート HTML 等の重厚な基盤（必要になった時点で昇格）

## 4. アーキテクチャ

採用アプローチ: **段階ハイブリッド**（実装は軽量なスキル拡張型、ただし findings スキーマとチェック関数の分離だけは Phase 2 再利用を見据えて設計する）。

```text
リポジトリルート/
├── qa/                                  # QA成果物（パッケージ配布に含めない）
│   ├── findings/
│   │   └── 2026-07-first-names.jsonl    # 疑義台帳（実行単位で1ファイル）
│   ├── verified.json                    # 検証済みキャッシュ（エントリhash → 判定）
│   └── reports/
│       └── 2026-07-first-names.md       # 人間向けサマリ
├── .claude/skills/
│   ├── validate-dataset/                # 【拡充】決定的チェック
│   │   └── scripts/
│   │       ├── validate.py              # エントリポイント（既存を拡充）
│   │       └── checks.py                # 【新規】チェック関数群（Phase 2 で import 可能）
│   ├── qa-review/                       # 【新規】LLMチェックの手順書スキル
│   └── qa-apply/                        # 【新規】承認済み修正の一括適用スキル
└── tests/
    └── test_validate.py                 # 【新規】変換器・チェック関数の単体テスト
```

### 4.1 決定的レイヤー（validate.py 拡充）

- **読み⇔ローマ字照合**: ひらがな→ローマ字変換器を実装。単一の正解を仮定せず、以下の許容方式それぞれで候補を生成し、実データがどの方式とも一致しない行のみ ERROR とする。
  - ワープロ式（長音をかな通り: `ろう→rou`、`しゅう→shuu`）
  - 長音省略式（`しゅう→shu`、`ああ→a`、`おう→o` 等、マクロン無しヘボン式）
  - 混合: 長音の出現箇所ごとに「かな通り」「省略」のどちらを選んでも良いものとして候補集合を生成し、実データがそのいずれかに一致すれば合格とする（`aichirou` のように行内で方式が揺れていても、各箇所が許容方式の範囲内なら ERROR にしない）
- **方式統計**: 各ファイルのローマ字方式の分布（ワープロ式 n%、省略式 m%、判定不能 k 件）をレポートに出力する。修正はしない（Phase 3 の入力データ）。
- **クロスファイル整合性**: `*_opti.csv ⊆ *_org.csv`（読み・ローマ字・漢字リストの包含）、男女ファイル間で同一読みエントリの矛盾検出（情報としてレポート。男女両方に存在する名前は正当なため ERROR にはしない）。
- **既存チェック維持**: 列数・文字種・行内漢字重複・読み重複・姓の推定人数整数チェック。
- **構造分離**: 個々のチェックは `checks.py` の純関数（`check_xxx(rows) -> list[Finding]`）として実装し、validate.py は CLI ラッパーに徹する。

### 4.2 LLM レイヤー（/qa-review スキル）

手動でローカル Claude Code から実行する手順書スキル。

1. 対象 CSV を読み、`verified.json` に登録済みハッシュの行を除外（増分検証）。
2. 残りを 100 件程度のバッチに分割し、サブエージェントに並列判定させる。判定観点:
   - (a) 各漢字表記が当該読みで実在の日本人名として妥当か
   - (b) 人名でない語・スクレイピング残骸の混入がないか
   - (c) 収録ファイル（男性名/女性名/姓）の配置が妥当か
3. 疑義は findings.jsonl に追記。「問題なし」のエントリは verified.json にハッシュ登録。
4. 実行サマリを qa/reports/ に Markdown で出力。

### 4.3 適用レイヤー（/qa-apply スキル）

1. findings.jsonl のうち `status: approved` の項目のみを対象にする（承認は人間が JSONL の status を直接編集するか、レポート Markdown のチェックボックスで行い、apply 時に同期する）。
2. dataset CSV は PreToolUse フックで保護されているため、適用前にユーザーの明示承認を得る。適用は git ブランチ上で行う。
3. 適用後に validate.py + pytest を必ず実行。行数が変わる場合は README（日英）の件数表記と CLAUDE.md を同時更新する。
4. 適用済み findings は `status: applied` に更新して台帳に残す（監査証跡）。
5. `status: rejected`（誤検出）とされた findings のエントリは verified.json にハッシュ登録し、以後の /qa-review で再検出されないようにする。

## 5. findings スキーマ（Phase 2 と共有する安定契約）

```json
{
  "id": "fn-man-org:あいいちろう",
  "file": "first_name_man_org.csv",
  "entry": "あいいちろう,aichirou,愛一朗,愛一郎",
  "check": "kanji_reading_mismatch",
  "severity": "error",
  "confidence": "high",
  "evidence": "愛一朗を「あいいちろう」と読む用例が確認できない…",
  "proposed_fix": {"action": "remove_kanji", "value": "愛一朗"},
  "status": "pending",
  "detected_at": "2026-07-27",
  "detected_by": "qa-review v1"
}
```

- `check` の語彙: `format_error` / `romaji_reading_mismatch` / `kanji_reading_mismatch` / `not_a_name` / `wrong_gender_file` / `duplicate` / `cross_file_inconsistency`
- `proposed_fix.action` の語彙: `remove_row` / `remove_kanji` / `fix_romaji` / `fix_reading` / `move_to_file` / `none`（人間判断のみ）
- `status` の遷移: `pending → approved | rejected`、`approved → applied`
- 決定的チェックの findings も同スキーマで出力できるが、通常は CI のエラー表示で完結させ、台帳には LLM 判定のみ記録する。

## 6. エラーハンドリングと安全策

- 適用は必ず git ブランチ上で行い、diff レビュー→コミットで履歴を残す。ロールバックは git revert。
- `remove` 系の修正案は confidence=high のみをデフォルトの承認候補として提示し、medium 以下は根拠を読んで個別判断する。一括自動削除は行わない。
- verified.json のキーはエントリ内容のハッシュのため、行が変更されれば自動的に再検証対象に戻る。
- findings.jsonl はスキーマバリデータを通し、不正な findings（未知の check 種別、entry と file の不一致等）は /qa-apply が拒否する。
- サブエージェントの判定が返らない・壊れている場合、そのバッチは記録せずスキップし、レポートに「未完了バッチ」として明示する（沈黙の欠落を防ぐ）。

## 7. テスト戦略

- ひらがな→ローマ字変換器の単体テスト: 拗音（きょ）・促音（いっ）・撥音（ん の後続 b/m/p での m 変換有無）・長音（おう/うう/ああ）の境界ケースを網羅。
- checks.py 各関数の単体テスト: 正常データ・違反データのフィクスチャで検証。
- findings スキーマバリデータのテスト: 不正 findings の拒否を確認。
- CI（test.yml）に validate.py 実行ステップを追加し、決定的チェックを毎 push 実行する。
- 既存の pytest スイート（パッケージ本体）は変更しない。

## 8. Phase 1 完了の定義

1. validate.py 拡充版が CI で全 CSV をパスする（既存データの決定的エラーを修正済み）。
2. 全エントリが /qa-review を一巡し、verified.json または findings.jsonl のいずれかに記録されている。
3. 承認された修正が適用され、クリーニング済みデータが v0.2.0 としてリリースされている。
4. README（日英）と CLAUDE.md の件数・仕様記述が実データと一致している。
